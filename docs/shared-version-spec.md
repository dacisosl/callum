# 동료용 공유 버전 시작 문서

이 문서는 **Padlet-Lite 의 동료 공유 버전을 다른 곳에서 새로 만들기 시작하는 사람**을 위한 것입니다. 지금 저장소의 앱(Next.js + Supabase + Vercel)은 그대로 두고, 동료 선생님들이 설정 없이 사본을 만들어 바로 쓸 수 있는 별도 앱을 만듭니다. 여기에는 원본 앱의 요구사항, 데이터 구조, 권한 규칙, 그리고 만들면서 실제로 부딪힌 문제와 해법을 모아 두었습니다. 새 작업을 시작하는 사람이 처음부터 다시 조사하지 않게 하려는 목적입니다.

원본: https://github.com/dacisosl/callum · 배포: https://callum-eight.vercel.app

---

## 1. 목적과 대상

**무엇을 위한 앱인가.** 교사가 보드를 만들어 링크 하나를 뿌리면, 연수생·학생이 로그인 없이 그 링크로 들어와 글과 사진·PDF 를 올리고, 서로의 글을 보는 도구입니다. 칼럼(섹션)마다 질문을 걸어 두면 답변을 모으는 설문판이 되고, 질문 없이 쓰면 자료 게시판이 됩니다.

**공유 버전이 다른 점.** 지금 앱은 만든 사람 한 명의 계정에 묶여 있습니다. 공유 버전은 **동료가 자기 계정에 사본을 만들어 자기 데이터로 쓰는 것**이 핵심입니다. 성공 기준은 하나입니다.

> 동료가 "사본 만들기 → 배포" 두 단계로 10분 안에 첫 보드를 공유할 수 있어야 한다.

계정을 새로 만들거나, 데이터베이스를 준비하거나, 설정 파일을 고치는 단계가 하나라도 끼면 이 기준을 통과하지 못합니다.

**왜 새로 만드는가.** 같은 목적을 지금 앱에 가입 기능을 열어 이룰 수도 있고(가장 쉽고 기능도 그대로), 각자 설치 안내서를 만들 수도 있습니다(데이터는 독립되지만 동료가 계정 세 개와 SQL 실행을 거쳐야 함). 사용자는 두 길을 검토한 뒤 **데이터를 각자 소유하면서 설정이 없는** 형태를 택했고, 그래서 새로 만듭니다. 이 결정은 다시 논의하지 않습니다.

## 2. 기술 방향과 그 대가

사용자가 꺼낸 후보는 **Google Apps Script 웹 앱 + Google Drive/Sheets 저장**입니다. 동료가 사본을 만드는 데 이보다 마찰이 적은 길은 없습니다. 구글 문서의 "사본 만들기" 가 그대로 앱 복사가 되기 때문입니다. 대신 감수할 것이 분명히 있습니다. 아래 표는 만들기 전에 반드시 읽어야 합니다.

| 항목 | 지금 앱 | Apps Script 로 가면 |
|---|---|---|
| 동료의 시작 | 계정 3개 + SQL 실행, 20분 | 사본 만들기 + 배포, 5분 |
| 실시간 반영 | 방송으로 즉시 | 없음. 주기 확인만 가능 |
| 동시 접속 | 수십 명 무리 없음 | 계정당 동시 실행 한도에 걸림. 30명이 한꺼번에 올리면 일부 실패 가능 |
| 저장 속도 | 0.1초 안 | 요청 왕복 0.3~1초 |
| 첨부 용량 | 1GB (Supabase 무료) | 15GB (Drive 무료, 메일·사진과 공유) |
| 파일 하나 크기 | 30MB | 현실적으로 10MB 안쪽 |
| 카톡 링크 미리보기 | 제목·이미지 표시 | 불가. 구글 기본 화면만 |
| 주소 | 고정 도메인 | `script.google.com/macros/s/…/exec` 고정 불가, 길고 낯섬 |
| 카톡 안에서 열기 | 정상 | 구글 샌드박스 창이라 로그인·표시가 어긋나기 쉬움 |

**Apps Script 한도(소비자 계정, 기억에 의존한 값이라 착수 전 공식 문서로 확인 필요).**

- 스크립트 실행 시간: 실행 한 번에 6분
- 동시 실행: 사용자당 30개
- URL Fetch: 하루 20,000회, 응답 50MB
- 트리거 총 실행 시간: 하루 90분
- 블롭(파일) 크기: 대부분의 서비스에서 50MB
- 웹 앱의 `google.script.run` 으로 넘기는 데이터는 base64 로 부풀어 실제 파일 크기의 약 1.3배

이 한도 아래에서 살아남는 설계 지침은 6장에 있습니다. 이 표를 보고 "그래도 이 길이 맞다" 고 판단해야 시작합니다. 그렇지 않다면 1장의 대안(가입 열기)으로 돌아가는 편이 낫습니다.

## 3. 기능 목록과 v1 범위

원본 앱의 기능을 전부 적고, 새 환경에서 **v1 에 넣을지 / 뒤로 미룰지 / 뺄지**를 표시했습니다. 판단 기준은 "연수 현장에서 없으면 안 되는가" 와 "Apps Script 에서 감당되는가" 두 가지입니다.

| 기능 | v1 | 이유 |
|---|---|---|
| 보드·칼럼 만들기, 이름 바꾸기, 삭제 | 넣음 | 뼈대 |
| 카드 작성·수정·삭제 | 넣음 | 뼈대 |
| 칼럼 안 정렬, 칼럼 간 이동, 칼럼 순서 바꾸기(끌어 놓기) | 넣음 | 화면 쪽 일이라 환경 무관. 저장은 느려도 됨 |
| 이미지·PDF 첨부 | 넣음 | 핵심. 단 파일 크기 상한을 10MB 로 낮춤 |
| 카드 타일 미리보기(이미지, PDF 첫 쪽, 유튜브 썸네일, 링크 대표 이미지) | 넣음 | 없으면 보드가 글자만 남음 |
| PDF 첫 쪽 썸네일 생성(브라우저 pdf.js) | 넣음 | 휴대폰 다운로드 문제 회피에 필수. 7장 참고 |
| 큰 이미지 자동 축소(긴 쪽 2000px) | 넣음 | 업로드 크기·속도 문제를 함께 줄임 |
| 클립보드 이미지 붙여넣기 | 미룸 | 편의 기능. 화면 코드 그대로 옮기면 되나 v1 검증 대상에서 제외 |
| 카드 크게 보기(뷰어), 이미지 전체 화면 | 넣음 | 뼈대 |
| PDF 뷰어(휴대폰은 쪽 단위 캔버스) | 넣음 | 7장 참고 |
| 유튜브·비메오 재생 | 넣음 | iframe 삽입만 하면 됨 |
| 링크 제목·설명·대표 이미지 가져오기 | 넣음 | `UrlFetchApp` 으로 서버에서 가능. 하루 20,000회 한도 안 |
| 카드 배경 색, 칼럼 색 | 넣음 | 화면 쪽 일 |
| 댓글(보드별 켜고 끄기) | 미룸 | 별도 표와 화면이 필요. v1 은 카드 본문으로 충분 |
| 공유받은 사람의 글쓰기(보드별 켜고 끄기) | 넣음 | 이 앱의 존재 이유 |
| 공유받은 사람이 자기 글 수정·삭제 | 넣음 | 열쇠 방식 그대로. 5장 참고 |
| 질문 섹션 | 넣음 | 연수 답변 수집의 핵심 |
| 첫 댓글 미리보기 | 뺌 | 댓글을 미루므로 함께 |
| 카드 검색, 칼럼 접기 | 넣음 | 화면 쪽 일 |
| 자동 저장, 실행 취소 | 넣음(자동 저장) / 미룸(실행 취소) | 실행 취소는 저장이 느린 환경에서 꼬이기 쉬움 |
| 보고 있는 보드가 주소에 남기, 뒤로가기 | 미룸 | Apps Script 웹 앱은 주소 조작이 제한적. 해시(`#board=…`)로 가능하나 v1 뒤로 |
| 실시간 반영 | 뺌 | 방송이 없음. 대신 "새 글 N개" 표시와 새로고침 버튼, 30~60초 주기 확인 |
| 읽기 전용 공유 링크, 홈에서 링크 목록 | 넣음 | 뼈대 |
| 카톡 링크 미리보기(제목·이미지) | 뺌 | 불가. 대신 공유 안내 문구를 함께 복사 |
| 고정 도메인 | 뺌 | 불가 |
| 무료 사용량 대시보드 | 미룸 | Drive 용량은 `DriveApp.getStorageUsed()` 로 셀 수 있어 나중에 붙이기 쉬움 |
| 쓰이지 않는 첨부 파일 정리 | 넣음 | 15GB 라 급하지 않지만 규칙 코드가 이미 있어 비용이 낮음. 7장 참고 |
| 보드 복사(칼럼 골라서) | 미룸 | 규칙 코드는 그대로 쓸 수 있음. v1 뒤로 |
| 모바일 터치 끌기, 칼럼 탭 | 넣음 | 연수생은 대부분 휴대폰 |
| 동영상 업로드 차단 | 넣음 | 한 줄 |

v1 은 "넣음" 만 만듭니다. 미룬 것은 화면 코드가 대부분 있어 뒤에 붙이기 쉽습니다. 뺀 것은 환경 때문이라 다시 검토하지 않습니다.

## 4. 데이터 모델

원본의 구조를 그대로 옮깁니다. 필드 이름과 뜻은 `lib/board-types.ts` 와 하나도 다르지 않아야 합니다. 그래야 7장의 순수 규칙 코드를 손대지 않고 가져올 수 있습니다.

```ts
interface Attachment {
  id: string;                 // "file-" + UUID
  name: string;               // 원래 파일 이름(한글 유지)
  kind: "image" | "pdf";
  mimeType: string;
  size: number;               // 바이트
  url: string;                // 볼 수 있는 주소
  storagePath?: string;       // 저장소 안 위치(Drive 면 파일 ID)
  thumbnailUrl?: string;      // PDF 첫 쪽 JPEG
  thumbnailPath?: string;
}

interface LinkPreviewData {
  url: string; title: string; description: string;
  image?: string; icon?: string; siteName?: string;
}

type CardTone = "default" | "yellow" | "peach" | "rose" | "lilac" | "sky" | "mint" | "slate";

interface BoardCard {
  id: string;                 // "card-" + UUID
  title: string;
  body: string;
  attachments: Attachment[];
  link?: LinkPreviewData;
  tone?: CardTone;
  authorName?: string;        // 주인이 쓴 카드의 표시 이름
  guestAuthor?: string;       // 손님이 쓴 카드의 이름. 있으면 손님 글
  editKeyHash?: string;       // 손님 수정 열쇠의 SHA-256 지문(16진수). 5장
  createdAt: number;          // 밀리초
  updatedAt: number;
}

interface BoardColumn {
  id: string;                 // "column-" + UUID
  title: string;
  collapsed: boolean;
  hue?: number;               // 0~360. 없으면 기본색 222
  question?: string;          // 있으면 질문 섹션. 최대 500자
  cards: BoardCard[];         // 새 카드는 맨 앞
}

// 댓글. v1 에서는 미루지만 구조는 정해 둡니다. 보드 데이터와 따로 저장합니다.
interface CardComment {
  id: string;                 // "comment-" + UUID
  boardId: string;
  cardId: string;
  author: string;             // 비우면 "익명"
  body: string;               // 최대 1000자
  createdAt: number;
  byOwner: boolean;           // 주인이 로그인한 채 남긴 댓글
}

interface BoardData {
  id: string;                 // "board-" + UUID
  title: string;
  columns: BoardColumn[];
  ownerId?: string;
  shareEnabled: boolean;
  shareToken: string;         // 32자 16진수. 비어 있으면 공유 안 함. 보드마다 고유
  commentsEnabled?: boolean;
  guestPostEnabled?: boolean; // 손님 글쓰기 허용
  createdAt: number;
  updatedAt: number;
}
```

**저장 방식 제안.** 두 가지가 가능하고, 동시 쓰기 때문에 두 번째를 권합니다.

1. **보드 하나 = Drive 의 JSON 파일 하나.** 구조가 그대로라 코드가 단순합니다. 대신 손님 여럿이 동시에 글을 올리면 마지막에 저장한 사람이 앞사람 글을 덮어씁니다. `LockService` 로 줄을 세워야 하고, 그러면 30명이 몰릴 때 뒤 사람은 몇 초를 기다립니다.
2. **보드·칼럼은 JSON 파일, 카드는 Sheets 의 한 행씩.** 카드 추가가 `appendRow` 한 번이 되어 동시에 여럿이 올려도 서로 덮어쓰지 않습니다. 카드 행에는 `boardId, columnId, cardId, order, json, createdAt, updatedAt` 을 두고 `json` 열에 카드 전체를 문자열로 넣으면 구조를 펼치지 않아도 됩니다. 읽을 때 보드 JSON 과 카드 행을 합쳐 위 `BoardData` 로 만들어 화면에 넘깁니다.

어느 쪽이든 화면 코드는 `BoardData` 하나만 보게 하고, 저장 방식은 서버 함수 안에 가둡니다.

**ID 규칙.** `접두어-UUID`. 카드·칼럼 복제나 보드 복사 때 반드시 새 ID 를 만듭니다. 같은 ID 가 두 곳에 있으면 정리·수정·삭제가 엉뚱한 것을 건드립니다.

## 5. 권한 모델

역할은 둘뿐입니다.

- **주인**: 스크립트를 배포한 구글 계정. 모든 보드를 읽고 씁니다.
- **손님**: 공유 링크(`?share=토큰`)로 들어온 익명 사용자. 로그인 없음.

Apps Script 웹 앱을 "나로 실행, 누구나 접근" 으로 배포하면 손님의 요청도 **주인 권한으로 서버 함수가 돕니다.** 데이터베이스가 대신 막아 주는 것이 없으므로 **모든 검사를 서버 함수 안에서 코드로 직접** 해야 합니다. 화면(클라이언트)의 검사는 편의일 뿐, 보안은 서버 함수가 전부 맡습니다.

서버 함수마다 지켜야 할 규칙입니다.

| 함수 | 통과 조건 |
|---|---|
| 공유 보드 읽기 | 토큰이 비어 있지 않고, 정확히 일치하는 보드가 있고, `shareEnabled` 가 참 |
| 손님 카드 추가 | 위 조건 + `guestPostEnabled` 참 + 대상 칼럼이 실제로 있음 + 제목 120자·본문 3000자 이내 + 첨부 10개 이내 + 보드당 카드 2000개 이내 |
| 손님 카드 수정·삭제 | 위 조건 + 그 카드가 있음 + `editKeyHash` 가 비어 있지 않음 + 보낸 열쇠의 SHA-256 이 지문과 일치 |
| 손님 파일 업로드 | 공유 중이고 글쓰기 허용인 보드의 폴더에만. 형식은 이미지·PDF, 크기 상한 이내 |
| 주인 기능 전부 | 요청자가 스크립트 소유자와 같은 계정(`Session.getEffectiveUser()` 비교) |

**손님이 자기 글만 고치는 방법(열쇠 방식).** 손님은 신원이 없으므로, 글을 올릴 때 브라우저가 무작위 열쇠(UUID 두 개 이어붙임)를 만들어 `localStorage` 에 카드 ID 별로 저장하고, 서버에는 그 열쇠의 SHA-256 지문만 카드에 남깁니다. 수정·삭제 때 열쇠를 보내면 서버가 지문을 다시 계산해 맞을 때만 통과시킵니다. 지문은 보드 데이터에 들어가 손님 모두에게 읽히지만, 지문으로는 열쇠를 되돌릴 수 없어 남의 글은 못 고칩니다. 제약은 **글을 올린 브라우저에서만** 고칠 수 있다는 것입니다. 이 제약은 화면에 그대로 적어 줍니다.

Apps Script 에서 SHA-256 은 `Utilities.computeDigest(Utilities.DigestAlgorithm.SHA_256, key, Utilities.Charset.UTF_8)` 로 계산하고 16진수 문자열로 바꿔 저장합니다.

**공유 토큰**은 32자 16진수 무작위 값으로, 공유를 끄고 다시 켜도 유지하고 "새 링크 만들기" 를 눌렀을 때만 바꿉니다. 옛 링크를 끊는 것이 목적이기 때문입니다.

## 6. Apps Script 에서 살아남는 설계 지침

2장의 한도 아래에서 연수 현장(30명이 10분 안에 동시에 글·사진 올리기)을 버티려면 다음을 지킵니다.

1. **카드는 추가 전용으로 저장한다.** 4장의 2번 방식(Sheets 행). 보드 JSON 은 주인만 고치고, 손님은 행만 덧붙입니다. 이것만으로 동시 쓰기 충돌의 대부분이 사라집니다.
2. **주인이 보드를 저장할 때 손님 카드를 덮어쓰지 않는다.** 주인 화면이 보드 전체를 통째로 저장하는 구조라면, 저장 직전에 서버에서 최신 카드 목록을 읽어 내 화면에 없는 손님 카드를 합칩니다. 원본 앱에서 이걸 빠뜨려 손님 글이 사라지는 사고가 있었습니다(`withGuestCards`).
3. **잠금은 짧게.** 보드 JSON 을 고치는 서버 함수만 `LockService.getScriptLock()` 을 잡고, 10초 안에 못 잡으면 "잠시 뒤 다시" 로 실패시킵니다. 카드 추가에는 잠금을 걸지 않습니다.
4. **주기 확인은 30초 이상, 화면이 보일 때만.** `document.visibilityState` 가 `visible` 일 때만 서버를 부릅니다. 탭으로 돌아왔을 때 한 번 즉시 확인합니다. 실시간을 약속하지 말고 화면에 "새 글 N개 · 새로고침" 을 보여 줍니다.
5. **파일은 10MB 상한.** 이미지는 올리기 전에 브라우저에서 긴 쪽 2000px 로 줄입니다(원본 앱의 `shrinkImage` 규칙). PDF 는 그대로 올리되 첫 쪽 썸네일을 브라우저에서 만들어 함께 올립니다. `google.script.run` 으로 base64 를 넘기면 서버에서 `Utilities.newBlob` 으로 되돌려 Drive 에 저장합니다.
6. **Drive 파일은 공개 링크로 읽게 한다.** 첨부 파일에 "링크가 있는 모든 사용자 보기" 권한을 주고 `https://drive.google.com/uc?id=…` 또는 `thumbnail?id=…&sz=w2000` 형태의 주소를 `url` 에 저장합니다. 카톡 인앱을 포함해 어디서든 `<img>` 로 바로 보입니다. 폴더 구조는 `Padlet-Lite/{보드ID}/` 로 보드마다 나눕니다. 7장의 정리 규칙이 이 구조를 전제로 합니다.
7. **긴 주소는 짧은 주소 서비스로 감싼다.** `script.google.com/macros/s/…/exec?share=…` 는 카톡에서 보기 흉하고 잘리기 쉽습니다. 공유 창에 "짧은 주소 만들기" 안내(bit.ly 등)나 QR 코드 생성을 넣습니다. QR 은 `https://chart.googleapis.com` 이 아닌 클라이언트 라이브러리로 만듭니다(구글 차트 QR 은 중단됨).
8. **화면은 한 번에 실어 보낸다.** HTML Service 는 요청마다 전체 페이지를 만듭니다. 화면 코드·스타일을 한 HTML 파일에 넣고, 데이터는 `google.script.run` 으로 따로 받습니다. 첫 화면에 보드 데이터를 함께 심어 왕복 한 번을 줄입니다.
9. **동시 실행 한도를 넘었을 때의 화면을 미리 만든다.** "지금 사람이 많습니다. 5초 뒤 다시 시도합니다" 를 자동 재시도와 함께 보여 줍니다. 원본 앱에는 없던 상황이라 새로 설계해야 합니다.

## 7. 원본 앱에서 배운 교훈

새 환경에서도 그대로 다시 걸릴 것들입니다. 각 항목은 실제로 겪고 고친 것입니다.

**안드로이드와 카톡 인앱 브라우저는 PDF `<iframe>` 을 파일 다운로드로 넘긴다.** 보드를 열자마자 "파일을 다운로드하려고 합니다" 창이 떴습니다. 해법은 PDF 를 절대 `<iframe>` 에 넣지 않는 것입니다. 카드 타일은 올릴 때 만든 첫 쪽 JPEG 썸네일을 쓰고, 뷰어는 휴대폰에서 pdf.js 로 쪽마다 캔버스에 그립니다. pdf.js 는 **legacy 빌드**를 써야 옛 안드로이드 웹뷰에서도 돕니다(최신 빌드는 `Map.prototype.getOrInsertComputed` 같은 새 문법을 써 깨집니다). 관련 코드는 `lib/pdf-render.ts` 입니다.

**주인 화면의 통째 저장이 손님 글을 지운다.** 6장 2번. 손님 글이 주 용도인 앱에서는 사고가 아니라 기본 상태가 됩니다. 저장 전 병합이나 추가 전용 저장 중 하나는 반드시 넣습니다.

**질문 섹션의 답변 카드는 제목이 선택이다.** 비워 두면 작성자 이름을 제목으로 저장합니다. 서버 검사가 제목을 필수로 요구하더라도 이 규칙으로 통과합니다. 남의 글을 주인이 고칠 때는 그 카드의 원래 작성자 이름을 써야 작성자가 조용히 바뀌지 않습니다.

**카드·칼럼 복제로 여러 카드가 같은 파일을 가리킬 수 있다.** 첨부 정리는 "어느 카드가 쓰는 파일" 을 **집합**으로 모아 판단해야 한 카드를 지워도 다른 카드의 파일이 살아남습니다. `lib/attachment-sweep.ts` 의 `referencedPaths` 가 그 규칙입니다.

**첨부 정리는 두 가지 안전장치를 둔다.** 편집창에 붙여 둔 파일은 저장소에는 있지만 아직 카드에 없으므로 **올라간 지 일정 시간(자동 24시간, 수동 10분)이 지난 것만** 지웁니다. 그리고 판단 기준 보드는 화면의 것이 아니라 **서버에서 막 읽어 온 것**을 씁니다. 손님이 방금 올린 글이 내 화면에 없을 수 있기 때문입니다.

**보드를 복사하면 첨부 파일도 새 보드 폴더로 복사한다.** 경로만 베끼면 복사본이 원본 폴더를 가리키고, 정리 기능이 원본 카드 삭제 시 그 파일을 지워 복사본이 깨집니다. Drive 에서는 `file.makeCopy(새폴더)` 로 합니다. 규칙은 `lib/board-copy.ts` 에 있습니다.

**공유 링크에는 고정 주소만 쓴다.** 원본에서는 배포마다 바뀌는 주소를 링크에 넣어 옛 화면이 열리는 혼란이 있었습니다. Apps Script 는 배포 ID 가 곧 주소라 "새 배포" 를 만들면 주소가 바뀝니다. **기존 배포를 "수정" 으로 갱신**해야 주소가 유지됩니다. 이 점을 사본 만들기 안내(9장)에 꼭 적습니다.

**권한 검사는 실행 주체를 기준으로 생각한다.** 원본에서 손님 업로드 정책이 주인 전용 표를 조회하도록 되어 있어, 손님에게는 그 조회가 항상 0건이 되고 업로드가 전부 거부되었습니다. Apps Script 는 반대로 모든 것이 주인 권한으로 돌아 아무것도 막히지 않습니다. 어느 쪽이든 "이 검사는 누구의 권한으로 도는가" 를 함수마다 적어 두고 확인합니다.

**설정 스크립트는 짧게, 여러 번 실행해도 안전하게.** 원본에서 긴 SQL 을 붙여 넣다 잘리고, 편집기가 문장을 오해해 끼워 넣는 일이 반복되었습니다. Apps Script 에는 SQL 이 없지만 "처음 실행 시 폴더·시트 만들기" 같은 초기화 함수가 생길 것입니다. 이미 있으면 건너뛰도록 만들어 몇 번을 눌러도 같은 결과가 나오게 합니다.

**앱이 스스로 준비 상태를 알려 준다.** 원본은 공유 설정 창에서 서버에 빠진 기능이 있는지 확인해 알려 줍니다. 공유 버전에서는 "Drive 폴더가 있는가, 시트가 있는가, 권한 승인이 끝났는가" 를 첫 화면에서 확인해 안 된 것을 버튼으로 바로 고칠 수 있게 합니다. 동료가 막히는 지점을 스스로 알 수 있어야 문의가 줄어듭니다.

## 8. 그대로 가져갈 수 있는 코드

저장소와 무관한 순수 규칙 모듈입니다. 타입만 맞으면 어느 환경에서든 동작하고, 각각 노드에서 돌리는 검사가 함께 있습니다.

| 파일 | 역할 | 옮길 때 |
|---|---|---|
| `lib/board-types.ts` | 데이터 모델과 상수(카드 색, 칼럼 색, 질문 길이) | 그대로 |
| `lib/board-copy.ts` | 보드 복사 규칙. 고른 칼럼만, 새 ID, 공유 해제, 열쇠 지문 제거, 옮길 파일 목록 | 그대로. `copyPath` 만 Drive 폴더 규칙으로 |
| `lib/attachment-sweep.ts` | 어느 카드도 가리키지 않는 파일 판정, 나이 기준, 참조 집합 | 그대로 |
| `lib/rpc-errors.ts` | 빠진 기능 목록 만들기 | 판정 대상만 바꿔서 |
| `lib/pdf-render.ts` | PDF 첫 쪽 썸네일 생성, 쪽 단위 캔버스 렌더링(브라우저) | 그대로. legacy 빌드 유지 |
| `app/styles.css` | 카드 타일, 칼럼, 뷰어, 편집창, 휴대폰 배치 | 클래스 이름 유지하면 대부분 재사용 |

화면 컴포넌트(`app/board-app.tsx`)는 React 이고 Supabase 호출이 22곳에 섞여 있어 통째로는 못 옮깁니다. 대신 **화면 구조와 문구**는 그대로 참고합니다: 카드 타일 순서(미리보기 → 제목 → 링크 줄 → 본문 → 첨부 수 → 작성자·시각), 편집창 순서(질문 → 이름 → 제목 → 내용 → 색 → 링크 → 첨부), 공유 창의 스위치 세 개(읽기 전용 링크, 글쓰기, 댓글), 질문 섹션의 "답변 쓰기" 버튼과 3줄 말줄임.

## 9. 동료의 사본 만들기 흐름

동료가 실제로 밟을 단계입니다. 안내 문서는 이 순서로, 화면 그림과 함께 씁니다.

1. 공유받은 구글 시트(또는 Apps Script 프로젝트)를 열고 **파일 → 사본 만들기**. 자기 Drive 에 복사됩니다.
2. 사본에서 **확장 프로그램 → Apps Script** 를 열고, 오른쪽 위 **배포 → 새 배포**.
3. 유형 **웹 앱**, "다음 사용자 인증 정보로 실행" 은 **나**, "액세스 권한이 있는 사용자" 는 **모든 사용자**. 이 두 설정이 틀리면 손님이 들어올 수 없습니다.
4. **권한 승인** 창이 뜹니다. 구글이 "확인되지 않은 앱" 경고를 보여 주면 **고급 → 안전하지 않은 페이지로 이동** 을 눌러야 합니다. 여기서 대부분 멈추므로 안내에 그림을 꼭 넣습니다.
5. 나온 **웹 앱 주소**가 그 사람의 앱 주소입니다. 이 주소는 이후 코드를 고칠 때 **배포 → 배포 관리 → 수정** 으로 갱신해야 유지됩니다. "새 배포" 를 누르면 주소가 바뀌어 이미 뿌린 링크가 옛 화면을 가리킵니다.
6. 주소를 열면 첫 화면이 Drive 폴더와 시트를 스스로 만들고 준비 상태를 보여 줍니다(7장 마지막 항목).

원본 프로젝트를 고쳐 배포할 때, 동료의 사본은 **자동으로 따라오지 않습니다.** 사본은 복사 시점의 코드로 멈춰 있습니다. 갱신 방법(새 사본을 만들고 시트 데이터만 옮기기, 또는 라이브러리로 코드를 공유하기)은 v1 뒤에 정합니다. v1 에서는 "사본은 복사한 날의 버전" 이라고 명확히 알립니다.

## 10. v1 완료 기준

아래를 실제로 해 보고 모두 통과해야 v1 입니다.

1. **동료 시작**: 이 문서를 처음 보는 동료가 9장의 안내만 보고 10분 안에 사본을 만들고 첫 보드의 공유 링크를 카톡으로 보낼 수 있다.
2. **연수 부하**: 휴대폰 30대가 같은 공유 링크로 들어와 10분 안에 각자 글 1개와 사진 1장을 올린다. 실패한 요청은 자동 재시도로 결국 모두 올라가고, 사라진 글이 없다.
3. **카톡에서 열기**: 안드로이드와 아이폰의 카톡 인앱 브라우저에서 링크를 열어 PDF 카드가 있는 보드를 봐도 다운로드 창이 뜨지 않는다.
4. **손님 수정·삭제**: 글을 올린 브라우저에서만 "내 글 수정" 과 "삭제" 가 보이고, 다른 기기에서는 보이지 않으며, 남의 글은 어떤 방법으로도 고쳐지지 않는다.
5. **주인 저장 안전**: 주인이 보드를 열어 둔 채 손님이 글을 올리고, 주인이 칼럼 색을 바꿔 저장해도 손님 글이 남아 있다.
6. **질문 섹션**: 질문을 걸어 둔 칼럼에서 제목 없이 답만 써도 올라가고, 타일에 작성자 이름이 제목 자리에 보인다.
7. **파일 정리**: 카드를 지운 뒤 하루가 지나 보드를 열면 그 첨부가 Drive 에서 사라지고, 다른 카드가 함께 쓰던 파일은 남는다.
8. **한도 상황**: 동시 실행 한도를 넘긴 상황을 인위적으로 만들어도 화면이 멈추지 않고 재시도 안내가 뜬다.

## 11. 시작하는 사람에게

- 먼저 2장의 표를 읽고 이 길이 맞는지 다시 판단하십시오. 맞다면 6장의 지침을 설계의 전제로 삼습니다.
- 4장의 데이터 모델은 바꾸지 마십시오. 바꾸면 8장의 코드를 쓸 수 없습니다.
- 5장의 권한 표를 서버 함수 하나하나에 대응시켜 검사 목록으로 만드십시오.
- 7장은 "이미 밟은 지뢰" 입니다. 같은 자리에서 다시 멈추지 않게 설계 초기에 반영하십시오.
- 한도 숫자는 착수 전에 https://developers.google.com/apps-script/guides/services/quotas 에서 다시 확인하십시오. 이 문서의 값은 기억에 의존한 것입니다.
